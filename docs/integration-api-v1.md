# ARAVA Integration API v1

## Назначение

ARAVA CRM остаётся локальной offline-first системой. Каждое устройство работает со своей SQLite, а сервер ARAVA хранит каноническое состояние и упорядоченный журнал изменений. Файл `arava.db` никогда не передаётся и не объединяется. Базовый путь — `/api/integration/v1`; несовместимые изменения требуют новой версии.

## Подключение и аутентификация

`POST /pair` принимает `{ apiVersion: "v1", deviceId, pairingCode }` и возвращает `{ apiVersion: "v1", deviceStatus: "ACTIVE", deviceToken }`. Код одноразовый, токен ограничен одним устройством и поддерживает отзыв/ротацию. Пароли CRM не передаются.

Последующие запросы содержат:

- `Authorization: Bearer <device-token>`;
- `X-ARAVA-Device-ID: <uuid>`;
- `X-ARAVA-API-Version: v1`.

Токен хранится Electron `safeStorage` вне SQLite, не журналируется и не возвращается renderer-процессу.

## Endpoints

- `POST /pair` — регистрация устройства.
- `GET /health` — версия API, время сервера, состояние регистрации.
- `GET /device/status` — `ACTIVE`, `REVOKED` или `ROTATION_REQUIRED`.
- `POST /sync` — одна идемпотентная операция.
- `POST /sync/batch` — до 25 операций.
- `GET /changes?after=<cursor>` — входящий журнал после подтверждённой позиции устройства.
- `GET /devices` — безопасное состояние подключённых устройств для владельца CRM.
- `POST /publications/media` — защищённая загрузка JPG/PNG/WEBP до 10 МБ.

Batch-запрос содержит `apiVersion`, `deviceId` и `operations`. Каждая операция содержит `entityType`, `entityId`, `operation`, `version`, `updatedAt`, `baseRevision`, `idempotencyKey`, `payload`. Подтверждение содержит каноническую операцию и payload, новую ревизию, глобальный `serverSequence` и статус `ACCEPTED` либо `CONFLICT`. CRM отмечает запись завершённой только после полного валидного подтверждения.

`GET /changes` возвращает не более 100 изменений за страницу, новый cursor, `hasMore` и размер канонического набора. Cursor сохраняется локально только после успешного транзакционного применения страницы.

## Ошибки

Формат: `{ "code": "DEVICE_REVOKED", "message": "..." }`.

Коды: `AUTH_REQUIRED`, `DEVICE_REVOKED`, `VALIDATION_ERROR`, `VERSION_UNSUPPORTED`, `CONFLICT`, `RATE_LIMITED`, `TEMPORARY_ERROR`.

Timeout, network error, HTTP 429 и 5xx повторяются с backoff. Ошибки данных, версии и авторизации остаются в журнале без агрессивных повторов. `DEVICE_REVOKED` очищает токен, но сохраняет outbox.

## Сущности и разрешённые поля

- `BRANCH`: реквизиты филиала, активность и архив.
- `ROOM`: филиал, вместимость, описание, оформление, активность и архив.
- `TRAINER`: только рабочее имя, активность, специализации, группы и филиалы.
- `GROUP`: идентификатор, публичные параметры, филиал, тренеры, статус.
- `STUDENT_IDENTITY` и `STUDENT_CONTACT`: рабочая карточка ученика и контакты.
- `GROUP_MEMBERSHIP`: ссылки student/group, активность, статус и даты.
- `SCHEDULE`: ссылки group/branch/room/coach, weekday/time/validity/status.
- `LESSON`: безопасные ссылки, начало/окончание и статус.
- `SUBSTITUTION`, `CARD`, `TARIFF`, `SUBSCRIPTION`, `SUBSCRIPTION_LEDGER`, `ATTENDANCE`, `STUDENT_NOTE`.

Исключены: `passwordHash`, временные пароли, recovery-коды, `securityVersion`, sessions, токены, audit, платежи, возвраты, долги, касса, расходы, зарплата и утверждённые расчёты. Платежи и возвраты намеренно отложены до отдельной безопасной политики финансового слияния.

## Outbox, порядок и конфликты

SQLite-триггеры создают outbox-запись в той же транзакции, что локальное изменение. Один worker объединяет последовательные ещё не отправленные изменения одной сущности и отправляет до 25 операций в порядке зависимостей. Сервер дедуплицирует `idempotencyKey`; повтор возвращает исходное подтверждение.

Каждая сущность имеет серверную ревизию. Если `baseRevision` отстаёт и payload отличается, сервер сохраняет обе версии в журнале конфликтов и не перезаписывает каноническую запись. Конфликт виден владельцу и не разрешается автоматически. Для штрихкодов дополнительно действует глобальная уникальность.

Входящие изменения применяются с флагом `integration.applyingRemote`, поэтому SQLite-триггеры не создают эхо-операцию. Повторная доставка пропускается по ревизии. Первичный запуск на пустом устройстве загружает серверный журнал; если и локальная база, и сервер уже заполнены, автоматическое объединение блокируется состоянием «Требуется первичное согласование».

Worker запускается при старте, после локальных изменений, раз в минуту, при фокусе окна и вручную. Интернет-сбой не отменяет локальную операцию.

Worker запускается после инициализации приложения и может продолжать отправку уже подготовленных безопасных операций после выхода CRM-пользователя. Он аутентифицируется только credential устройства и не имеет доступа к паролям пользователей. Выход из учётной записи не удаляет регистрацию устройства.

## Backup и устройство

Outbox и журнал входят в SQLite backup. Device ID и токен находятся вне БД: перенос backup не клонирует авторизацию, на новом компьютере требуется подключение. Восстановленная очередь сохраняется.

## Чаты ARAVA-WEB

Для чатов источник истины — сервер ARAVA-WEB: CRM не зеркалирует историю в
SQLite. Main-процесс получает список и страницы сообщений через узкие методы
`ChatService`; renderer не выполняет HTTP-запросы напрямую.

- `GET /chats` — фильтры, поиск и `updatedSince`;
- `GET /chats/:conversationId` — безопасная карточка;
- `GET /chats/:conversationId/messages?limit=50&before=...` — cursor pagination;
- `POST /chats/:conversationId/messages` — plain text и стабильный
  `clientMessageId`;
- `POST /chats/:conversationId/read` — studio-side отметка чтения.

К device headers добавляется сформированный service layer заголовок
`X-ARAVA-CRM-Context` только с `userId`, ролью, именем и доступными филиалами.
Renderer не формирует этот контекст. ChatService повторно проверяет локальные
группы и филиалы: OWNER имеет полный доступ, ADMIN ограничен филиалами, COACH
видит только свои регулярные/ассистируемые групповые чаты и не видит личные.

Если сервер недоступен после уже разрешённого открытия разговора, сообщение
попадает в существующий `SyncOutbox` как `CHAT_MESSAGE`. Состояния интерфейса:

Публикации передаются как сущность `PUBLICATION`. DTO содержит только стабильный ID,
тип, текст, период видимости, безопасного автора, `mediaRef` и цели по CRM ID.
Черновики не синхронизируются. Повторная операция с тем же ключом идемпотентности
возвращает прежнее подтверждение; новый version обновляет существующую публикацию.
«Ожидает отправки», «Отправлено», «Ошибка». Повтор использует тот же
`clientMessageId`; сервер сохраняет одну логическую запись. Outbox входит в
обычный backup, постоянная история — нет, потому что остаётся на сайте.

UI обновляет список и открытую страницу раз в 20 секунд, при открытии и фокусе
окна. Query keys содержат user ID, роль и отсортированный branch scope; logout
очищает TanStack Query cache. Содержимое сообщений не попадает в глобальный
поиск, Attention Center или экран клиента.

## Ограничения

- 4.4C реализован: приватный и групповой чат; групповой доступ определяется активным `GROUP_MEMBERSHIP`;
- 4.4D реализован: публикации для всех клиентов, филиалов, групп и тренеров.

Автоматического UI-разрешения конфликтов и синхронизации платежей/возвратов пока нет.
Синхронизация между CRM-устройствами не даёт личному кабинету права изменять
посещаемость или локальные финансовые данные.
